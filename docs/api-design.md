# API Design

Base URL: `http://localhost:8000` (local), `/api` (behind the frontend's nginx proxy in production — see `frontend/nginx.conf`).

All request/response bodies are JSON. Full interactive docs are auto-generated by FastAPI at `/docs` (Swagger)
and `/redoc` — this document is the human-readable companion, not a duplicate of the OpenAPI schema.

## Conventions

**Auth:** `Authorization: Bearer <token>`, obtained from `POST 
/auth/token`. See Roles below.

**Correlation ID:** every request should carry `X-Correlation-Id` (the frontend generates one per request if absent — see `frontend/src/app/core/interceptors/correlation-id.interceptor.ts`). The backend echoes it back on the response and threads it through every log line and `DeploymentEvent` written as a result of that request.

**Error envelope** — every non-2xx response has this exact shape:
```json
{ "error": { "code": "STRING_CODE", "message": "human-readable", "details": {} } }
```
`code` is what client code should branch on. Current codes: `NOT_FOUND` (404), `CONFLICT` (409 — idempotency collision, optimistic-concurrency loss, or in-flight-environment serialization), `VALIDATION_FAILED` (422 —
includes the PRODUCTION-requires-APPROVED governance gate), `FORBIDDEN` (403 — RBAC), plus standard 401 (missing/invalid token) which is not domain-shaped (comes from FastAPI's own auth dependency).

**Roles:** `admin`, `approver`, `operator`, `viewer`. See the per-endpoint table below for who can call what.

## Auth

### `POST /auth/token`
Form-encoded (`application/x-www-form-urlencoded`), OAuth2-password-style:
`username` (one of `admin`/`approver`/`operator`/`viewer`), `password`
(ignored — demo only, see `app/core/security.py`).

Response `200`: `{ "access_token": "...", "token_type": "bearer" }`

## Health

### `GET /health`
No auth required.
Response `200`: `{ "status": "ok" | "degraded", "components": { "database": "ok" | "error: ..." } }`

## Model Registry

| Endpoint | Roles | Notes |
|---|---|---|
| `POST /models` | admin, operator | 409 `CONFLICT` if name already exists |
| `GET /models` | any authenticated | `?search=` substring filter on name |
| `GET /models/{model_id}` | any authenticated | 404 if missing |
| `POST /models/{model_id}/versions` | admin, operator | New version always starts at `DRAFT` |
| `GET /models/{model_id}/versions` | any authenticated | Newest first |
| `POST /models/versions/{version_id}/promote` | approver, admin | See Promotion below |
| `GET /models/{model_id}/metrics` | any authenticated | See Monitoring below |

**`ModelCreate`**: `{ name, description?, owner_team? }`
**`ModelVersionCreate`**: `{ version_label, framework, algorithm, artifact_uri, training_data_ref?, tags?, created_by? }`

**Promotion** — `PromotionRequest`:
```json
{ "to_stage": "VALIDATED", "approved_by": "approver", "decision": "APPROVED", "reason": null, "expected_row_version": 1 }
```
- `expected_row_version` implements optimistic concurrency (architecture.md
  Q2) — mismatch returns `409 CONFLICT` with the current value in `details`.
- `to_stage` must be a legal direct transition (`ALLOWED_PROMOTIONS` in
  `app/models/model.py`) or `422 VALIDATION_FAILED`. **`PRODUCTION` is
  never a legal promotion target** — it's only reached via a successful
  deployment (see below).

## Deployments

| Endpoint | Roles | Notes |
|---|---|---|
| `POST /deployments` | operator, admin | Returns `202` (newly scheduled, async) or `200` (idempotent replay) |
| `GET /deployments` | any authenticated | Filters: `?model_version_id=&environment=&status=` |
| `GET /deployments/{id}` | any authenticated | Poll this to watch a deployment finish |
| `POST /deployments/{id}/retry` | operator, admin | Only valid from `FAILED`; `?simulate_failure=true\|false` optional |
| `POST /deployments/{id}/rollback` | operator, admin | Only valid from `SUCCEEDED`, and only if a prior `SUCCEEDED` deployment exists for the same `(model, environment)` |

**`DeploymentCreate`**:
```json
{
  "model_version_id": "...", "environment": "PRODUCTION",
  "idempotency_key": "client-generated-unique-string",
  "requested_by": "operator", "simulate_failure": null
}
```
- `idempotency_key` is required and unique — a repeat with the same key   returns the **existing** deployment (`200`, `created` semantics not re-run), never a duplicate row.
- `simulate_failure` is demo/test-only (see ADR-001's simulated runtime) — omit it in normal use for randomized outcomes.
- Deploying to `PRODUCTION` with a version not in `APPROVED` (or already `PRODUCTION`) fails fast with `422 VALIDATION_FAILED` **before** any async work starts.
- A second deployment request for the same `(model, environment)` while one is still in flight (non-terminal status) fails with `409 CONFLICT`.

**Execution is asynchronous** (ADR-001): the `202` response body has `status: "REQUESTED"`. Poll `GET /deployments/{id}` (or watch `deployment.events` grow) until `status` is one of `SUCCEEDED`, `FAILED`,`ROLLED_BACK`.

**`Deployment` response shape** includes the full `events` array (`DeploymentEvent[]`: `from_status`, `to_status`, `message`, `correlation_id`, `reconciled`, `created_at`) — this is what backs the Event Timeline view; there's no separate events endpoint.

## Monitoring

### `GET /models/{model_id}/metrics`
Any authenticated role. Returns every `MetricSnapshot` across every version of the model, newest first:
```json
{ "model_id": "...", "snapshots": [ { "model_version_id": "...", "environment": "PRODUCTION", "latency_ms_p50": 41.2, "...": "..." } ] }
```
Snapshots are seeded automatically the first time a version reaches `PRODUCTION` and refreshed periodically by a background task — there's no manual"record a metric" endpoint in the minimum API surface

## What's intentionally NOT in the API

- No `DELETE` on any resource — the take-home's lifecycle model treats `ARCHIVED` as the terminal "removed" state, never a hard delete, so the audit trail (`ApprovalRecord`, `DeploymentEvent`) is never orphaned.
- No bulk/batch endpoints (batch-approve, batch-rollback) — noted as a near-term roadmap item, not needed for the acceptance scenarios.
